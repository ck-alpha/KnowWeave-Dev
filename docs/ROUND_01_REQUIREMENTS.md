# KnowWeave — Round 01：独立项目初始化与本地知识库闭环

## 你的角色与总体目标

你是这个项目的主要工程开发 Agent。请基于当前本地工作区已有的开源 LLM Wiki 代码，完成 **KnowWeave** 的第一轮二次开发，使其成为可以继续迭代、能够用于实习简历展示的个人项目。

项目定位：**本地优先的 Agent 智能知识管理系统**。重点保留并理解“原始文档 → LLM Ingest → 可维护的 Wiki → 检索问答/来源追溯”的工作流。用户已在本地通过 Ollama 部署了 Qwen。后续计划加入 BM25 + Embedding + RRF 混合检索和检索评测，但这不是本轮的实现任务。

**工作原则：** 先审阅实际源码与环境，再自主选择最小、稳健的实现路径。你可以自行决定适当的文件组织、命令、实现方式和问题修复措施，不必逐项等待用户批准。不要为了架构完美而扩张任务；要交付真正可运行的功能和可核对的结果。

## 本轮任务

### 1. 了解并接管现有工程

- 阅读现有 README、核心源码、现有项目文档与测试，确认技术栈、运行入口、Wiki Ingest、检索、问答及 Ollama 模型接入的真实调用链。
- 判断哪些功能可以直接保留，哪些原有品牌、示例数据、部署或商业化内容不再适合个人项目。以低风险重命名和收敛为主，不进行无关重构。
- 检查本机 Node/pnpm、Ollama 的可用性和已安装模型，优先使用现有 Qwen；不要假设具体模型 tag、硬件或系统设置。如果缺少必要依赖，先尝试合理的轻量修复。

### 2. 建立 KnowWeave 身份和本地运行闭环

- 将项目对用户的展示名称、主要 README、基本应用标识调整为 **KnowWeave**，形成自己的产品定位和真实的功能说明，不保留原产品的营销文案、线上服务入口或无关介绍。
- 让用户能够在本地启动应用，通过 Ollama + 已安装的 Qwen 完成 **添加文档 → Ingest → 形成/更新 Wiki 页面 → 问答 → 查看来源** 的最小真实闭环；对必要配置提供简明说明。
- 基于既有架构优先修复关键兼容性问题，不要求本轮实现新的向量检索、MCP 服务或新的数据库服务。
- 注意本项目是对 MIT 开源实现的二次开发。**可以使用独立 GitHub 仓库、不设置 `upstream` 远端、不显示 GitHub Fork 标识，但必须保留原代码要求的 LICENSE 原作者版权/许可声明及其他依法需要保留的 NOTICE；不得通过删除版权声明来伪装从零原创。** 在合适的第三方说明文件中准确记录代码来源和自有改造范围；不用把上游项目品牌放在产品 UI 的主视觉位置。

### 3. 引入一个现成数据集并运行小样例

- 本项目唯一必选数据集：**BEIR SciFact**。官方资料：https://github.com/beir-cellar/beir ，下载地址：https://public.ukp.informatik.tu-darmstadt.de/thakur/BEIR/datasets/scifact.zip 。
- 数据包含 `corpus.jsonl`、`queries.jsonl`、`qrels/test.tsv`。设计**可重复执行的数据下载/读取流程**，避免手工复制文件；本轮只需选取数量有限、主题适当相关的 SciFact 文本，跑通 Wiki Ingest 与少量问答演示。
- 暂不要求将全部 5,183 篇文档交给 Qwen 逐篇 Ingest。后续的检索基准应直接使用 SciFact 的原始 corpus / queries / qrels，同一评测集合上公平比较方案，而不是把小型 Wiki 演示数据冒充完整 benchmark。
- 不要直接把下载的数据文件、大型缓存、模型文件、个人数据库、密钥、用户私有文档提交到 Git；保留自动下载脚本及数据集来源、许可、使用说明即可。

### 4. 建立持续交付与开发记录

- 建立简明而持续维护的项目文档，至少覆盖：**项目现状/架构、当前进度、开发日志、Round 01 验收报告**。目录和格式可按现有仓库惯例决定，但要容易在下一轮找到。
- 开发日志应记载日期、实际完成的任务、关键技术决策、问题与解决方式、测试结论、下一步事项。必须区分“已实现”“尚未实现”“计划实现”，不允许编造测试结果。
- 检查并运行仓库适当的测试、构建以及端到端验证；如果本机 Ollama、依赖或网络使某项验证无法完成，要写明受限步骤和可复现方式。
- 将改动提交 Git。如果配置了个人 GitHub 远端且具备权限，推送到个人仓库（推荐在三轮开发期间保持为 **private**，最后公开）；如尚未配置 GitHub 仓库，只提供最少的设置指令，不要误推到原项目的远端。

## 本轮验收条件

1. 本地应用能够启动并正确使用现有的 Ollama + Qwen；没有必须使用付费云端 API 的强制依赖。
2. 真实完成一次小样本 SciFact 导入、至少一次 Wiki 内容生成或更新，以及一次带可检查来源的检索问答（如果环境失败，则清楚记录原因与重现步骤）。
3. 代码和文档以 KnowWeave 为新项目组织；原有开源版权和必要的许可说明正确保留。
4. 后续开发者可以根据文档明确找到 BM25/FTS5 检索入口、将来可接入 Embedding/Hybrid 的位置、SciFact 的数据流程。
5. 测试/构建结果、开发日志、Round 01 验收报告以及 commit SHA 均可检查。

## 本轮明确不做

- 暂不实现向量索引、Hybrid Retrieval、RRF 或全量数据集评测（留到 Round 02）。
- 暂不加入 MCP、GraphRAG、复杂多 Agent、用户登录、云服务或微服务。
- 不为追求展示效果而大规模重写现有功能。

## 结束时的交付方式

完成代码开发、文档更新、必要测试与 Git 提交/推送。最后以简洁的报告告诉我：**完成事项、启动和复现方式、实测结果、核心文件位置、尚存问题、Git commit SHA/个人仓库链接（如已推送）**。

请直接开始检查当前工作区并开展 Round 01。除确实需要用户提供的凭据或权限之外，不必反复就微观实现细节提问，自主做出合适的工程判断。
