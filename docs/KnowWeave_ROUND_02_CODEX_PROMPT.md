# KnowWeave — Round 02 Codex 开发任务

## 你的角色与本轮目标

你是 KnowWeave 项目的主要开发 Agent。仓库：`https://github.com/ck-alpha/KnowWeave`，当前工作基于私有 `main` 分支。本轮在 Round 01 已跑通的“原文 → Qwen Ingest → Wiki → Query → 来源追溯”基础上，**用最小合理改动实现真正进入实际问答路径的本地混合检索，并跑出可信的 SciFact 全量检索评测**。

请先阅读 `README.md`、`architecture.md`、`docs/PROGRESS.md`、`docs/DEVLOG.md`、`docs/ROUND_01_ACCEPTANCE.md`、`docs/SCIFACT.md` 与现有关键检索代码，再自主决定最简单稳健的实现方案。**不要按照固定的函数/文件/数据表设计机械照做；根据真实代码自行设计、实现、测试。** 不必反复询问小的技术决策。优先可用、可信、可复现，不追求过度工程化。

## 本轮任务

### 任务一：基线检查与一个复现问题的修正

- 核实 Round 01 当前真实功能和代码状态，继续沿用本地 Ollama 与已有 `qwen3.8:27b`，保持现有启动和 Wiki 数据兼容。
- 纠正 README 关于 `python3 scripts/scifact.py prepare` “自动下载数据”的表述与源码行为不一致问题：让干净环境可以按照明确的、真实有效的步骤获取数据并准备样例。
- 必要时修复影响本轮工作的关键缺陷；不要为了整理历史代码而全面重构。

### 任务二：加入本地 Embedding 与混合检索

- 优先选择通过 Ollama 运行的 `nomic-embed-text`（如实际环境不适合，可基于测试选择更合适的本地模型并说明原因）。已有 Qwen 继续负责 Wiki 知识生成与问答，Embedding 模型只负责向量表示。
- 保留已有 SQLite FTS5/BM25 方案，新增可持久化、可复用的本地向量检索能力，并实现 **BM25 / Embedding / Hybrid（RRF 融合）** 三种检索模式。
- **必须把新的检索能力真正接入 Wiki Query 的取证与回答链路**，不能仅另写一个孤立的 benchmark；至少让实际提问能够使用 Hybrid，并提供简单可验证的方式切换或比较三种模式。保留现有可信引用与无证据处理机制。
- 考虑 Wiki 页面创建、内容更新、删除及启动后同步对应的向量索引维护；不要让旧页面/旧内容长期残留在检索结果里。模型未下载、服务不可用或索引尚未准备时应清楚提示，并尽量确保原有 BM25 工作流不被破坏。
- 选择依赖最少的索引与存储方案；不强制引入独立向量数据库、微服务或大型框架。不要在每次普通查询时重复全量生成文档向量。

### 任务三：基于 SciFact 做真实、可复现的三路检索评测

- 复用 Round 01 的 SciFact 下载与数据校验能力，基于 **官方原始 `corpus.jsonl`、`queries.jsonl`、`qrels/test.tsv`** 完成完整检索评测。正常目标为原始 5,183 篇 corpus 和 300 条 test queries；实际数量以数据校验为准。
- 基准评测直接索引**原始论文标题/摘要**，不得为了评测而让 Qwen 将全部 corpus 编译为 Wiki；不要把 2～3 篇小样本 Wiki 的问答数据冒充 SciFact 全量检索测试。
- 对 BM25、Embedding、Hybrid 使用一致的语料、query、相关性标注和评测规则，尽可能复用真正用于产品检索的核心逻辑；至少输出 **Recall@10、nDCG@10、MRR@10**，同时记录实际语料量、query 数、Embedding 模型与版本、关键检索参数、索引耗时、查询延迟（建议 p50/p95）和运行环境。
- 保留可重新运行的命令或脚本、结构化实验结果与简明对比说明。不要根据 test 集标签逐题调整 RRF 参数或作弊优化。若 Hybrid 没有提升，要如实报告并分析，而不是编造正向指标。
- 如果完整测试遇到确实无法排除的环境障碍，保留失败记录并如实标明“部分运行”，不能把子集指标写作全量结果；优先解决低成本障碍后完成完整评测。

### 任务四：验证真正的在线效果与索引一致性

- 真实演示一次基于现有 Wiki 内容的三路检索（或至少 BM25 与 Hybrid 差异），确认 Hybrid 返回的页面确实进入 Qwen 的回答上下文并保留可点击的来源引用。
- 通过有代表性的测试验证：语义措辞不同的查询、页面更新后的重建或增量刷新、页面删除、模型/索引异常、无结果与无证据回答、不同 Wiki 之间的索引隔离（如果现有多 Wiki 结构需要）。
- 跑相称的单元/集成测试，以及适用的 typecheck、lint、build；不得用单元测试替代真实 Ollama + SciFact 的实验。

### 任务五：开发文档、验收记录和 Git 交付

- 实现过程中持续更新 `docs/DEVLOG.md`，记录实际技术选择、遇到的问题、取舍及修复方式。
- 更新 `docs/PROGRESS.md`、根目录 `architecture.md`、`README.md`（安装、模型下载、检索模式、索引构建及评测复现），以及确有必要的已有文档。
- 新增 `docs/ROUND_02_ACCEPTANCE.md`，清楚区分“代码已实现 / 本机实测 / 未验证 / 未完成”。保留可核查的评测结果、运行命令、当前 commit、模型信息、主要代码入口、限制和下轮建议。如记录结构化 JSON，优先把可公开的简明摘要纳入 `docs/evidence/`，大文件和个人环境信息继续留在 `.local/`。
- 进行适当的 Git commit，并推送到用户独立的 `ck-alpha/KnowWeave` **私有**仓库 `main`；不要推送第三方仓库。保留现有 MIT `LICENSE` 和 `NOTICE.md`；不要把模型、SciFact 原始数据、向量缓存、数据库、token、私人文档提交 Git。

## 验收口径

1. **在线功能**：在实际 Wiki Query 中能使用 BM25、Embedding、Hybrid（RRF）检索，最终答案仍能追溯到真实 Wiki 页面和原始来源；索引更新/删除后不会持续返回陈旧页面。
2. **离线对比**：基于 SciFact 原始全量数据、同一测试 query 和 qrels，真实输出三路检索的 Recall@10 / nDCG@10 / MRR@10 及运行代价，数据量和运行参数可核查。
3. **复现能力**：其他开发者按文档可准备本地 Embedding、运行在线 Wiki 测试并重现检索评测；本地 Ollama/Qwen 现有工作流保持可用。
4. **工程质量**：相关回归测试、类型检查、构建完成；已知失败如实记录，不夸大性能、原创范围或测试覆盖。
5. **交付与文档**：架构、开发日志、进度、Round 02 验收报告及 Git 提交同步更新、推送完成。

## 本轮不做

- 不添加 MCP、GraphRAG、复杂 Agent 编排、分布式向量数据库、用户登录、SaaS、云部署等扩展。
- 不用大型重构替代必要功能；不花费时间追求 UI 大改或发布营销素材，留给 Round 03。
- 不以“脚本能算检索指标”代替“功能已接入真实 Wiki 问答”。
