# KnowWeave — 私有开发仓库改名与公开源码仓库建立（Codex 任务）

## 任务目标

请在已完成三轮开发和公开前检查的 **KnowWeave** 本地工作区继续执行。本任务仅处理仓库命名、源码发布与隐私隔离，不是新一轮功能开发，不需要新增功能或重构系统。

最终形成两个**完全独立的 Git 仓库**：

- `ck-alpha/KnowWeave-Dev`：原开发仓库，继续 **Private**，完整保留现有分支、提交历史、开发 Prompt、验收报告、评测证据及开发日志。原有本地工作目录继续作为这个私有仓库的工作区。
- `ck-alpha/KnowWeave`：全新 **Public** 展示仓库，只有整理后的最终源码、基本使用说明与必须保留的许可证、归属说明。**必须使用全新 Git 历史、全新初始提交，不是 Fork，不得包含原私有仓库的 `.git` 或其历史。**

## 任务一：检查并安全重命名私有仓库

1. 先检查本地 Git 状态、远端 `main`、当前 GitHub 仓库可见性、认证及目标名称是否可用，确认没有尚未推送的工作。记录本次导出的精确源提交 SHA。
2. 将目前的 `ck-alpha/KnowWeave` GitHub 仓库重命名为 `ck-alpha/KnowWeave-Dev`，**保持 Private**；严禁删除、清空、强制推送、压缩或改写历史。
3. **在创建新的 `KnowWeave` 仓库之前**，将原本地工作区的 `origin` 明确改成 `ck-alpha/KnowWeave-Dev`，检查 fetch/push URL 都是新私有地址，确保将来继续开发不会误推至公开仓库。不要依赖 GitHub 旧地址重定向。
4. 适当更新**私有仓库当前版本**中仍指向旧仓库 URL 的 README、开发文档和 GitHub 链接为 `ck-alpha/KnowWeave-Dev`，以免新公开仓库占用原地址后这些链接指错仓库；可以正常追加文档提交，但不要修改任何历史提交。记录本次公开快照实际对应的源码提交 SHA。
5. 确认原开发仓库提交历史、已有文档与所有源码均完整保留。如 GitHub CLI 凭据/管理权限不足，停下来说明需要用户完成的具体操作，不能执行危险替代方案。

## 任务二：在独立目录准备公开的源码快照

从已经验收的私有仓库当前 `main` 导出一个**无 Git 历史**的快照，放到独立目录。尽量采取“明确纳入文件”的方式，而不是将私有项目整体复制后再盲目删减。

**公开仓库允许保留：**
- 构成项目实际功能的源码，例如 `apps/`、`packages/`、`scripts/`、`tests/` 中的适用代码，以及运行所需的静态 UI 资源；
- 构建与依赖配置，例如 `package.json`、`pnpm-lock.yaml`、工作区及 TypeScript/Vitest/格式化配置；
- 简洁的 `README.md`（做什么、核心功能、技术栈、关键调用链、安装配置、启动、基本使用、如何执行测试和独立 benchmark）；
- 必需的 `LICENSE`、`NOTICE.md`、`.gitignore`、`.env.example` 等。

**公开仓库不要包含：**
- 所有三轮开发任务 Prompt、公开前检查 Prompt、`AGENTS.md`、根目录用于开发 Agent 的 `CLAUDE.md` 等提示词/开发过程指令；
- `docs/` 下的轮次需求、验收报告、开发日志、进度、职业准备、面试提纲、独立审阅指南、证据 JSON、实验结果、历史截图与相关过程资料。为了保持“源码展示”边界，**此版公开仓库不复制整个 `docs/` 目录**；
- 本地运行状态、SQLite、模型、向量缓存、下载的数据集、个人 Wiki、密钥、日志、临时构建产物及其他私人信息；
- 私有开发仓库的 Git 元数据、私有仓库地址、历史 commit SHA 链接、内部个人机器绝对路径或个人邮箱。

可保留**能够执行 benchmark 的源码与数据下载脚本**，但不要上传 benchmark 的实测结果文件、验收结果表格或排名记录；README 仅说明如何在用户机器上复现，不需要展示三轮开发历程或量化结果。

基于实际依赖判断哪些文件属于必要源码；如果某个必需资源目前在 `docs/`，可将该资源迁到恰当的源码/资源路径并修正引用，但不要把过程文档重新带进公开仓库。确保删去文档后所有 README 链接、运行脚本和构建配置仍有效。

## 任务三：新建同名公开仓库并检查隔离性

1. 确认 `ck-alpha/KnowWeave` 名称已释放后，创建**新的** `ck-alpha/KnowWeave` 仓库，设为 **Public**，不是从私有仓库执行 Fork；不要触及 `KnowWeave-Dev` 的可见性。
2. 在快照目录中 `git init`，使用 GitHub noreply 提交身份生成**全新的初始提交**，配置该目录的 `origin` 指向 `ck-alpha/KnowWeave` 并推送到 `main`。不要把私有仓库的任何旧提交或分支推过去。
3. 检查公开仓库可从无授权环境访问，源码与必要文档可以独立克隆、安装、构建；核对公开提交历史只有快照提交（如需要整理追加提交须保持简洁）。
4. 检查私有仓库仍为 Private，原工作区的 `origin` 是 `KnowWeave-Dev`，公开快照工作区的 `origin` 是 `KnowWeave`。两个仓库不得互设 upstream 或交叉推送。

## 任务四：发布验证与交付

- 在公开快照目录执行与之相称的依赖安装、测试、类型检查、Lint、生产构建。根据环境条件可运行现有小型 Demo，但不要为此重新开发功能，且本地数据/结果绝不能提交到公开仓库。
- 对**新公开仓库所有已跟踪文件与初始提交**进行安全检查：确认没有私人路径、作者个人邮箱、真实令牌、旧历史、Prompt、轮次验收、实验结果和不必要文件；核对 README 中没有无效的 `docs/` 链接。保留 MIT 原版权声明和准确的二次开发来源、贡献归属，不将继承代码声称为全部从零原创。
- 发布过程及完整验收情况可写入**原私有仓库**的开发日志或交付记录；**不要上传这些记录到公开仓库**。
- 最终向用户简洁报告：两个仓库地址及可见性、各自最新 SHA、公开仓库文件清单、测试和构建的实际结果、源码快照基线、两处 `origin`、历史与隐私隔离检查、尚未验证的事项。

## 工作方式和安全边界

请先自行阅读真实源码、Git 仓库状态与文档，再自主选择简单可靠的操作路径；不要为了发布而重构业务模块。遇到管理权限不足、仓库重命名失败、目标名称冲突、源仓库有未推送变更或隐私扫描异常时，应停止具有风险的步骤并说明情况，不能绕过检查继续发布。**绝不删除或覆盖私有仓库，绝不修改其历史，也绝不将它设为 Public。**

请直接开始。完成后按照用户约定的工作流提交发布结果，供 ChatGPT 再次核对两个 GitHub 仓库。
